# M1b frame p95 measurement, October 11, 2026

Performance is not an M1b exit gate. This is a local, synthetic scaling observation, not a hosted acquisition benchmark, hardware guarantee, or reason to add plan tiers.

## Build and method

- Apple M1 Pro, 16 GiB RAM, macOS 26.6.2, arm64.
- Google Chrome 154.0.8037.99, headless, 1280×720, device scale 1.
- Release Rust/WASM build on `web-mvp` base `7c07ae4192b9cdeabea7e25854e4f833b691109f` plus this PR's `max-files` restart change. Rust 1.98.1 and wasm-bindgen 0.2.129.
- WASM SHA-256: `4cdfb9668e94fc19aeb8ee987e6b5a2d16898e8c9e79f3447e46f69ddaf976cd`.
- Actual renderer reported **ANGLE / Vulkan SwiftShader**, despite requesting `--gpu gl`. These are software-renderer results on this Mac, not native Apple GPU measurements.
- Existing `scripts/perf/browser-bench.mjs`, fixed timestep 1/60, 360 measured ticks after full log parsing. `max-files=25000`, `hide=filenames,date`, `file-idle-time=0`, `seconds-per-day=1`.
- Every synthetic row adds one distinct file. Eight actors rotate across rows, all timestamps are `1735689600`; repository names are separate path prefixes. Source history is fully loaded, not shortened to the display cap.
- `frame p95` is the nearest-rank p95 of the existing engine's per-tick `last_sim_ms + last_build_ms + last_gpu_ms`. GPU timing here is **submission**, not completion. No `--finish` / GPU readback was requested. This is not a wall-clock animation interval or a guaranteed FPS estimate.
- Each scene used a fresh browser. Parsing/load and measured rendering are separate phases. No provider, account token, Git clone, server-side render, network acquisition, or real GitHub data was used.

The 50-prefix scene exceeds the illustrative 16.67 ms budget for 60 Hz even with the 25,000 displayed-file cap. Directory topology, actors, hardware, GPU backend and sampling all matter. There is no performance-exit claim. A display cap bounds visible files, not retained history, F1 credits, directory count, or publication-preview enumeration. Smaller-scene load times need not be monotonic because page/application startup, cache effects and run-to-run variation can dominate these single runs.

## Reproduce

Build the web release with the repository's existing `scripts/build-web.sh` and package build instructions. Serve that distribution and synthetic logs from the same loopback origin. Do not use production credentials or a hosted provider for this measurement.

Generate each scene using the following row rule, for `files` equal to 1,000 / 10,000 / 50,000 and `repositories` equal to 1 / 10 / 50 respectively:

```js
let log = '';
for (let i = 0; i < files; i++) {
  log += `1735689600|Actor${i % 8}|A|/repo${i % repositories}/dir${Math.floor(i / 100)}/file${i}.txt\n`;
}
```

For each scene, invoke the existing harness with its same-origin log path:

```sh
node scripts/perf/browser-bench.mjs \
  --base http://127.0.0.1:PORT --log /perf/SCENE.log \
  --gpu gl --mode fixed --frames 360 --viewport 1280x720 \
  --options 'max-files=25000&hide=filenames,date&file-idle-time=0&seconds-per-day=1' \
  --json /YOUR_PRIVATE_SCRATCH/SCENE.json
```

Check the JSON's actual renderer, loaded commit count, `fixed.peak.files`, directory count, frame summary and errors before comparing results. Record failures rather than excluding them. For hardware GPU or browser frame pacing claims, make a separate measurement with verified hardware renderer and realtime/readback metrics. This matrix deliberately does not establish those claims.
